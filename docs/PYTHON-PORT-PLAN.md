# Python port plan

**Status: plan only. No Python code exists yet; nothing here is implemented.**

This records the decisions already made about a native Python implementation of
`ag-ui-validate`, the reasoning behind them, and the concrete inventory/design work
needed to execute the port when it starts. It does not start the port.

## Decisions already made (not up for relitigation)

- **Native Python reimplementation**, not a wrapper that shells out to the Node CLI
  (a linter shouldn't drag a second runtime into slim containers and CI images) and not
  transpiled or a shared Rust/WASM core (both destroy the readable, zero-dep,
  easy-to-contribute property that is the reason a community adopts a conformance tool).
- **Same repo.** `spec/` ([catalog.json](../spec/catalog.json),
  [fixtures/](../spec/fixtures/)) is already shared, top-level, and language-neutral
  (see the M0 restructure). When the port starts, `src/` moves to `js/` and Python lands
  in `py/`. `action/` stays at the repo root permanently — GitHub Action convention, and
  it invokes the CLI as a black box regardless of which language builds it.
- **Naming:** PyPI `ag-ui-validate`, import package `ag_ui_validate`, console script
  `ag-ui-validate` — so `uvx ag-ui-validate <url>` and `npx ag-ui-validate <url>` are the
  same command with the same basic output.
- **Correctness contract is the shared fixture corpus, not shared code.** Both
  implementations run the identical `spec/fixtures/` corpus and must emit identical
  diagnostics. A CI parity job runs both across every fixture and diffs — the drift guard,
  and also what makes a third-party implementation possible (see §5).
- **The pytest plugin is the priority surface, more than the CLI.** Nearly every AG-UI
  *server* is Python (LangGraph, CrewAI, Google ADK, Pydantic AI, Agno, LlamaIndex), so
  Python is where the non-conformant emitters actually live. Landing in framework
  maintainers' own integration suites is the goal.
- **Timing:** the port starts after `spec/catalog.json` has stabilized against real
  captured streams. Porting a churning ruleset doubles the cost of every rule change.

## 2. What will be awkward — and what to change now

Honest finding: **there is very little in `src/` itself that resists a clean port.** No
generic type-level machinery, no structural-typing tricks, no clever conditional types —
the `noUncheckedIndexedAccess`/`exactOptionalPropertyTypes`/`verbatimModuleSyntax`
strictness sprinkled through the code (non-null assertions, `export type` splits) is pure
TypeScript-compiler ceremony that simply doesn't exist as a category of problem in
Python. The `createValidator` closure pattern (§1) is the only real "shape" translation,
and it's a clean, unambiguous one (closure → class).

The genuine difficulty is **not in `src/` — it's in the tooling that isn't hand-written
source**:

1. **Zod-schema introspection in `scripts/derive-lib.mjs` + `scripts/generate-event-table.mjs`
   (the `unwrap`/`fieldSpec`/`describe` functions).** These walk zod's internal `_def`
   representation (`ZodOptional`, `ZodDefault`, `ZodDiscriminatedUnion`, …) — entirely
   TS/zod-specific and not reducible by changing the TS code, because it's inherently
   tied to zod's object model. The Python side needs a **from-scratch** equivalent
   walking **pydantic v2** models instead (`model_fields`, `FieldInfo.annotation`,
   `typing.get_origin`/`get_args`, `Literal`, discriminated unions via
   `Field(discriminator=...)`). This isn't a port — it's new tooling built against a
   different SDK (`ag-ui-protocol` / `ag_ui.core` on PyPI, confirmed pydantic-based).
2. **`src/vitest/index.ts`'s `expect.extend` registration** has no pytest equivalent
   in kind — pytest plugins register via entry points and hook functions, not a global
   matcher registry. Replaced wholesale by a new pytest plugin module, not translated.

**Done, bundled into PM1:** the `CATEGORY` and `DEPRECATED` maps in
`generate-event-table.mjs` were hand-maintained plain JS objects (wire-type → category
string; wire-type → replacement name for `@deprecated` markers) — *data*, not
zod-specific logic, exactly the kind of language-neutral fact `spec/` was created in the
M0 restructure to hold. They're now [`spec/event-categories.json`](../spec/event-categories.json),
read by both `generate-event-table.mjs` and the new `py/scripts/generate_event_table.py`
(§7, PM1), instead of two hand-maintained copies drifting apart. Regenerating
`event-table.ts` after the hoist produced a byte-identical file — confirmed zero
behavior change on the TS side.

That hoist had a second payoff, also landed: `check-spec-links.mjs` used to import
`EVENT_TABLE` from the built JS `dist/` purely to read each event's `specUrl` — but
every one of those URLs turned out to be a *deterministic function* of the wire type
string itself (`EVENTS_DOC` + `wireType.toLowerCase().replace(/_/g, "")`, with a
category-based override for the deprecated `thinking` group), verified by diffing this
computation against all 33 entries of the built `EVENT_TABLE` (0 mismatches). So
`check-spec-links.mjs` no longer needs `dist/`, any SDK, or either language's build
output at all — it moved to the root [`scripts/`](../scripts/check-spec-links.mjs)
alongside `generate-rule-docs.mjs`, and Python never needs its own copy. The other five
`js/scripts/` tools (`build-fixtures.mjs`, `demo.mjs`, `fuzz.mjs`, `e2e-live-server.mjs`,
and the zod-introspection trio) don't have this out: they each test *this
implementation's* validator/transport/build against real behavior, so Python needs its
own independently-written equivalents (per the milestones below), not a shared file.

Everything else genuinely is a straightforward, low-risk translation.

## 3. Dependency budget

Target: **zero runtime dependencies** for the importable core, matching the TS side.
Three cases were named as likely-hard; a fourth turned out to be the real hard one.

| Case | Verdict | Reasoning |
|---|---|---|
| RFC 6902 JSON Patch application | **Vendor / hand-port, zero-dep** | `src/protocol/jsonpatch.ts` is ~220 lines of plain recursive dict/list traversal with no JS-specific behavior (see §1) — a direct, low-risk hand-port, same as the TS side chose. |
| SSE frame parsing | **Vendor / hand-port, zero-dep** | Python's `codecs.getincrementaldecoder("utf-8")` covers `TextDecoder(..., {stream:true})`; async generators are native. No library needed. |
| JSON Schema validation | **N/A — not actually used** | The TS "schema" check (`validateSchema` in `src/index.ts`, driven by `EventSpec.fields`) is a hand-rolled subset (`kind`/`required`/`enum`), not real JSON Schema — no `$ref`, `oneOf`, `allOf`, etc. It ports directly with zero dependencies; there is nothing here to replace. |
| **Async HTTP client for `validateEndpoint`** | **Real dependency, resolved: `httpx`, as an optional `[transport]` extra** | Not one of the three named cases, but the actual hard one. Node/browsers ship `fetch` as a *platform global* — that's why `src/transport/index.ts` has zero added runtime dependencies today; it's an accident of platform, not a discipline the TS code enforces. Python's standard library has no async, streaming-capable HTTP client. `httpx` exposes `response.aiter_bytes()`, giving access to raw chunk boundaries as they arrive — exactly what AGUI506 (keepalive gaps) and AGUI507 (buffered/unflushed responses) need to measure. Decided (§8, resolved before PM5 started): depend on `httpx` for `ag_ui_validate.transport` and the CLI's URL path, imported lazily, scoped to `pip install ag-ui-validate[transport]` rather than a required dependency — the importable core and the pytest plugin's *recorded-stream* path (the primary pytest-plugin use case — asserting on captured events, not live endpoints) stay genuinely dependency-free on a bare install. This is a real, not cosmetic, parity gap with the TS side's "zero deps" claim, and the one place it can't be closed like-for-like. |

Devlopment-only dependencies (mirroring `@ag-ui/core`/`vitest`/`tsdown`/`typescript` as
devDependencies on the TS side — never shipped):

- **`ag-ui-protocol`** (PyPI; import name `ag_ui`) — the official pydantic-based Python
  AG-UI SDK. Devdependency for the event-table derivation script and the
  sdk-alignment-equivalent tests (mirrors `@ag-ui/core`'s role exactly). `requires_python
  >=3.9`, depends on `pydantic>=2.11.2`.
- **`pytest`** — devDependency for running the suite, and the pytest-plugin's runtime
  peer (mirrors `vitest` being a `peerDependency` here).
- **`hatchling`** — build backend (§4).
- **A type checker** — see the open question in §8 (`pyright` vs. `mypy`).

## 4. Packaging

- **Build backend: `hatchling`**, with `spec/` force-included into the wheel so the
  catalog and fixture corpus ship inside the installed package — the same requirement
  the M0 restructure's `npm pack --dry-run` check enforces on the TS side. From
  `py/pyproject.toml`:

  ```toml
  [tool.hatch.build.targets.wheel.force-include]
  "../spec" = "ag_ui_validate/spec"
  ```

  Read at runtime via `importlib.resources.files("ag_ui_validate") / "spec" /
  "catalog.json"` — unlike the TS build, where tsdown *inlines* the JSON into the bundle
  at compile time, Python reads the shipped file at import time. Both approaches ship
  `spec/` in the distributable artifact; only the mechanism differs.

- **Console script:**

  ```toml
  [project.scripts]
  ag-ui-validate = "ag_ui_validate.cli:main"
  ```

  `main()` is a sync wrapper (`sys.exit(asyncio.run(_amain()))`) around the async CLI
  body, matching `src/cli.ts`'s `main().then(...)` shape.

- **Python version floor.** `ag-ui-protocol` requires `>=3.9`, but **3.9 is already
  past end-of-life as of this writing (2026-08-17; EOL was 2025-10)**, and 3.10 is close
  behind (EOL 2026-10). This mirrors exactly the reasoning behind the TS side's own
  `engines: ">=22"` decision (Node 20 EOL, not a technical Node-22-API requirement — see
  the M0 follow-up audit). Recommendation: **apply the same policy, not a fixed number**
  — target the oldest non-EOL CPython version at actual port kickoff time. As of today
  that would be **3.11** (EOL 2027-10); confirm against the current Python release
  calendar when the port actually starts, since "starts after the catalog stabilizes"
  means this could be many months out.

## 5. Parity CI design

Both implementations independently assert, in their own native test suites, that their
diagnostics equal `spec/fixtures/*/expected.json` — `test/fixtures.test.ts` on the TS side,
`py/tests/test_fixtures.py` (PM4, done) on the Python side. If both are green, they are
transitively equal to each other *for the fields both check byte-for-byte*. That alone is
*necessary* but not the strongest possible check — it doesn't exercise either shipped CLI,
only each language's internal validator call.

**Known, permanent exceptions the diff job must carry forward, not treat as regressions**
(both documented in `test_fixtures.py` and PM4's plan row above): `AGUI204`/`AGUI502`'s
`message` embeds each runtime's native JSON-parser error text, which will never match
word-for-word between V8 and Python's `json` module; `AGUI503`'s `message` embeds
`{sdkVersion}`, which will never match between `@ag-ui/core` and `ag-ui-protocol` since
they're versioned independently. A naive full-diagnostic-array `toEqual`-style diff would
flag all three on every single run. The CLI-to-CLI diff job needs the same
rule/severity/pointer/eventIndex-exact-but-message-tolerant comparison `test_fixtures.py`
already implements, not a blanket deep-equal.

**Recommended design: a direct CLI-to-CLI diff job**, not just "both test suites are
green":

- For every fixture in `spec/fixtures/` (both `stream.jsonl` and `scenario.json`
  variants), run it through **both shipped CLIs** with `--json` output
  (`node dist/cli.js --json <file>` and `uvx ag-ui-validate --json <file>` /
  `python -m ag_ui_validate --json <file>`, from a built wheel — not `python -m pytest`
  internals) and deep-diff the resulting `diagnostics` arrays.
- This is strictly more valuable than comparing each language's unit-test assertions,
  because it also exercises the actual packaging/CLI-wiring path (argument parsing,
  reporter formatting, exit codes) — a bug there wouldn't show up in either language's
  own fixture-runner test, only in a real cross-CLI invocation.
- **Failure output:** a per-fixture table — fixture path, TS diagnostics, Python
  diagnostics, and a structural diff — posted as the job's summary (GitHub Actions job
  summary markdown), not just a pass/fail flag, so a maintainer can see exactly which
  rule/field diverged without re-running locally.
- **Cadence** (mirroring the pattern already shipped for the SDK-drift job, §"related
  work" below): run on every PR that touches `spec/**`, `js/src/**`, or `py/**` (path
  filters keep this off unrelated doc/README PRs), *plus* a nightly scheduled run as a
  backstop against anything that slips through path-filter gaps or environment drift.
  Confirm this cadence in §8 — a stricter "PR-only" or looser "nightly-only" policy are
  both reasonable alternatives depending on how much CI cost the corpus's size ends up
  costing (currently 47 fixtures; will grow as both catalogs grow).

**Related work already shipped:** `.github/workflows/sdk-drift.yml` (added as part of
this same round of follow-up work) establishes the pattern this job should reuse — open
a PR on a clean, actionable diff; file a deduplicated issue when the check itself can't
run cleanly (there, a zod-derivation failure; here, e.g. a CLI that fails to build).

## 6. pytest plugin API sketch

**Registration** — a standard `pytest11` entry point, so the plugin activates on install
with no explicit import needed in the user's test files (simpler than the vitest side,
which requires `import "ag-ui-validate/vitest"` in a setup file):

```toml
[project.entry-points.pytest11]
ag_ui_validate = "ag_ui_validate.pytest_plugin"
```

**Assertion helper.** Pytest idiom favors `assert helper(...)` with pytest's assertion
rewriting for boolean-returning helpers, but the interesting content here is a
*multi-line diagnostic message* (mirroring the vitest matcher's `message()` — every
violated rule, its spec citation) that we want fully custom, not autogenerated. The
better fit is an `assert_*`-style helper that raises with a rich message on failure and
returns `None` on success (the same shape as `pandas.testing.assert_frame_equal` or
`pytest.approx`-adjacent conventions), not a boolean matcher:

```python
from ag_ui_validate.pytest_plugin import assert_valid_agui

def test_my_agent_stream(captured_events):
    assert_valid_agui(captured_events, features=["shared-state"], max_warnings=0)
```

`assert_valid_agui(received, *, features=None, severity_overrides=None,
max_warnings=None)` accepts the same shapes the TS matcher does — a list of event
dicts/JSON strings, or a JSONL string — and raises `AssertionError` with the joined
per-diagnostic lines (rule, severity, spec URL) when invalid.

**Validating a live endpoint from a test** — an async counterpart, usable directly with
pytest's native async support (or `pytest-asyncio`):

```python
from ag_ui_validate.pytest_plugin import assert_valid_agui_endpoint, validate_agui_endpoint

async def test_my_live_agent():
    await assert_valid_agui_endpoint("http://localhost:8000/agui", max_warnings=0)

async def test_inspect_report():
    report = await validate_agui_endpoint("http://localhost:8000/agui")
    assert report.summary.errors == 0
    assert report.features["shared-state"] == "exercised"
```

`validate_agui_endpoint` returns the full `Report` (for tests that want to inspect
feature-matrix or summary detail beyond pass/fail); `assert_valid_agui_endpoint` is the
one-line convenience wrapper, matching the sync/recorded pair above. Both live in the
same `httpx`-dependent code path flagged in §3 — the plugin's *recorded*-stream helper
(`assert_valid_agui`) stays dependency-free; only the endpoint-validating helpers pull in
`httpx`.

## 8. Open questions

1. ~~**The `httpx` dependency (§3).**~~ **Resolved, before PM5 started:** `httpx`
   (over `aiohttp` or hand-rolling streaming HTTP over stdlib `urllib`), and scoped to
   an **optional extra** — `pip install ag-ui-validate[transport]` — rather than a
   required dependency of the whole package. `ag_ui_validate.transport` and the CLI's
   URL code path import it lazily with a clear error if it's missing; the core
   validator and the pytest plugin's recorded-stream helpers (the primary pytest-plugin
   use case, per the decision that Python is where most non-conformant emitters live)
   stay genuinely dependency-free even after `pip install ag-ui-validate` with no
   extras. Mirrors the TS side's own `vitest` peer dependency, marked optional.

   hand-roll the Python arg parser (`cli_args.py`'s `_FLAGS` dict, a direct port of
